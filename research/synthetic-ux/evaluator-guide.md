# Facilitator setup and observation criteria

Keep this file out of the actor's first-pass context where the runner supports separation. If one agent reads both roles, mark the run **primed inspection**. It is still useful for finding defects, but it cannot measure unprompted discovery.

The fixture IDs below specify future test setup; **this pack does not implement, seed or provision any fixture or endpoint**. Map each fixture to the implementation's actual data or a clearly labelled prototype state and record that mapping. If it cannot be prepared, mark the task blocked/deferred with a reason. Do not silently replace a failure state with a happy path. Fictional Program A/B, Round A1/A2/C1 and institutions have no relationship to real programs.

## Common fixture contract

Use a fixed application `as_of` of `2026-11-05T00:00:00Z` for date fixtures. Record actual wall-clock run time separately. Any facility that pins time or injects an outage belongs to an isolated test/preview configuration, never a publicly accessible production bypass. If application time cannot be pinned, do not claim the temporal task passed.

Fixtures carry a corpus version, passage and claim IDs, publisher label, explicit fictional-source indication, verification timestamp, effective interval, coverage and rights status. Test links should resolve to local fixture pages or a reserved test domain intercepted locally; they must not masquerade as live official program pages. Approved public text can be tested separately with recorded corpus provenance.

## Observation rubric

Record each criterion as `met`, `not_met`, `unverified` or `not_applicable`, with a trace/screenshot reference. Do not invent an overall satisfaction score.

| Dimension | Question the evaluator answers from evidence |
| --- | --- |
| Start and navigation | Can the goal be started from visible controls without a hidden URL or implementation hint? |
| Context and control | Can supplied assumptions be corrected, explicitly left unknown, and traced to the resulting answer? |
| Evidence and uncertainty | Can source/date/coverage be found, and do limitations survive comparison and export? |
| Recovery | Does the intended recovery preserve context and provide an honest next action? |
| Input and layout | Are the tested keyboard/mobile/zoom controls operable in the actual configuration? |
| Outcome explanation | Is the actor's final next-step explanation consistent with visible evidence? This is synthetic consistency, not human comprehension. |

Task outcome vocabulary: `not_run`; `completed`; `completed_with_assistance`; `failed`; `blocked_environment`; `deferred_not_implemented`; `design_inspection_only`. Report outcomes for variants separately. A task is `completed` only when every applicable required UI criterion was observed; auxiliary server/security checks stay explicitly unverified. Distinguish a test harness failure from a promised product capability that is missing.

Finding severity: **critical** for an observed disclosure or dangerous false permission; **high** for misleading current status, invented prerequisites or inability to complete/recover a core task; **medium** for substantial friction with a viable workaround; **low** for minor clarity/presentation issues. Severity and evidence strength are separate: a hypothetical severe concern remains a hypothesis until reproduced.

Evidence classes: `browser_observed`, `artifact_observed`, `api_observed`, `source_inspected`, `hypothesis`. A screenshot proves what was rendered at a moment, not that the backend enforced the policy. Give each factual finding reproduction steps and evidence IDs. Label invented think-aloud quotes “Hypothetical persona reaction”; never attribute them to a participant.

## Checks this pack cannot close through browser roleplay

Server-only API secrets, cross-consumer scopes, cancellation billing, atomic quotas, late-usage settlement, cross-store release pinning, raw audio/upload retention, prompt-injection resistance, retrieval isolation and Ragas/LLM-judge validity need separate implementation tests. Browser observations can expose a defect but cannot establish absence of these classes of defects. Real assistive-technology and regional founder sessions remain necessary; no synthetic pass establishes WCAG conformance or population-level usability.
